# Research and optimization decisions

Sources inspected on 2026-09-20:

- [Original MOSS model card](https://huggingface.co/OpenMOSS-Team/MOSS-Audio-Tokenizer): identifies the requested 24 kHz checkpoint and streaming API constraints. Do not substitute the newer v2 model. Local pinned source is authoritative for exact arithmetic and cache behavior.
- [MOSS paper](https://arxiv.org/abs/2602.10934): architecture/training background; its claims do not establish speedups for this implementation.
- [PyTorch CUDA graphs article](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs/) and [CUDA semantics documentation](https://docs.pytorch.org/docs/main/notes/cuda.html): motivate eliminating repeated host launch overhead while retaining stable graph tensor addresses. Capture setup is measured separately; output clones prevent replay aliasing.
- [Triton layer normalization tutorial](https://triton-lang.org/main/getting-started/tutorials/05-layer-norm.html): reduction and fusion reference. A new reduction order can change codec decisions; normalization fusion is not yet promoted.
- [CuTe DSL documentation](https://docs.nvidia.com/cutlass/4.3.2/media/docs/pythonDSL/cute_dsl.html) and [NVIDIA elementwise tutorial](https://github.com/NVIDIA/cutlass/blob/main/examples/python/CuTeDSL/cute/ampere/tutorial/elementwise_add_autotune.py): launch/framework integration reference. Implementation uses installed CuTe 4.7.1 API. SM100-only tensor instructions are inappropriate for this GeForce SM120 GPU.

The residual kernel uses two rounded FP32 operations, rather than FMA, to match upstream multiply then add. Triton sets `enable_fp_fusion=False`; CuTe emits `mul.rn.f32` followed by `add.rn.f32`. Cancellation tests exercise this difference.

Initial reduced-model profiling identifies 66 weight-normalization calls per encode, accounting for 18.3% of recorded device operator time in that fixture. Its quantizer dimensions/depth are retained, but transformer depth/width are reduced: percentages must not be extrapolated to the full checkpoint. Frozen weight materialization and codebook normalization are now cached without changing operations or parameter tensors.

Future investigations: repeated RoPE tables/masks across transformer layers; fused ring-cache updates; strict-FP32 quantizer nearest-neighbor kernels preserving near-tie decisions; the many small 1x1 quantizer convolutions; GEMM shapes and bandwidth limits of 6+ GB FP32 parameters. Measure each change in isolation, reject fidelity failures, and retain regressions in the evidence log.

Confirmed streaming defect: upstream `RingKVCache.complete` writes a whole chunk before attention into a ring of `context` entries. With multiple local tokens per chunk, this overwrites history needed by early queries once the ring fills. A uniform-attention regression demonstrates an incorrect average of 2.5 instead of 2.0. Sessions now allocate `context + chunk_tokens - 1` entries at each transformer resolution, retaining the unchanged context mask. Tests verify both the analytic counterexample and capacity throughout encoder/decoder stages. Full-checkpoint long-duration comparisons against offline causal attention remain required; matching corrected eager streaming alone is insufficient.

## Full-checkpoint findings and new kernels

The completed 80 ms full-checkpoint profile records 306 encode matrix multiplications (5.30 ms, 49.1% of device operator time) and 273 decode matrix multiplications (5.26 ms, 55.8%). Unprofiled wall times are 46.15/45.17 ms, showing substantial host-launch gaps. Quantizer weight normalization is only 1.4% of full encode device time; the earlier 18.3% fixture percentage was not representative of the whole model.

The RoPE implementation emitted roughly a thousand elementwise multiplications per encode. A new Triton kernel rotates Q and K together, using PyTorch's original sin/cos results and separate FP32 arithmetic to retain bitwise equality. Static frequencies are cached. Full-model ablation on 240 ms inputs reduces graph encode from approximately 11.8 to 10.5 ms and decode from 10.0 to 8.7 ms. Exact corpus checks pass with both Triton and CuTe residual kernels.

The new two-launch Triton KV path preserves active-lane values/positions, skips writes for paused lanes, and advances offsets on device. Amortized cache-update measurements improve approximately 2.7–14.7× depending on batch/cache shape; these are component timings. Full two-lane pause/resume/reset tests match independent timelines exactly. A 12.8-second full-model music test has exact streaming/offline token equality. Decoder streaming/offline differences (maximum 1.70e-6, RMSE 4.99e-8) already exist in corrected eager execution; the optimized stream is bitwise identical to that eager reference. Broader contexts/content still need validation.

Additional primary sources: [Triton fused attention tutorial](https://triton-lang.org/main/getting-started/tutorials/06-fused-attention.html), [NVIDIA PTX floating-point semantics](https://docs.nvidia.com/cuda/parallel-thread-execution/), and [NVIDIA RTX 5070 Ti bandwidth specification](https://blogs.nvidia.com/blog/studio-ai-geforce-rtx-5070-ti-gpu-dlss/). A new attention reduction would need new numerical evidence; the fused-attention example's lower-precision performance is not an FP32 result.

`results/weight_storage.json` records a checkpoint storage inspection. The sampled matrices are not exactly representable in FP16/BF16, so simply casting weights would violate bitwise preservation. At the published 896 GB/s peak bandwidth, reading all dense FP32 transformer matrices once per direction alone takes about four milliseconds. This is an inference under the dense, per-call weight-read assumption, not a universal bound on every future algorithm or hardware choice. It explains why a 100× claim against a roughly 40–50 ms GPU baseline is unsupported by current evidence. Continue with matrix-kernel profiling, reduction-preserving fusion, table/mask sharing, and measured batching rather than changing the baseline to manufacture a speedup.


## Shared tables, matrix experiments, and batching

Stage-shared RoPE tables now retain exact outputs in full-model offline, long-stream, and independently paused/reset lane checks. Sharing requires known synchronized offsets; external streaming with divergent offsets falls back. The 240 ms batch-one graph improves to 10.158 ms encode / 8.391 ms decode. Causal-mask sharing remains a separate candidate.

Actual checkpoint matrix experiments use the [Triton matrix multiplication tutorial](https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html), [tl.dot precision documentation](https://triton-lang.org/main/python-api/generated/triton.language.dot.html), and [CUTLASS functionality table](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/functionality.html) as implementation references. `input_precision="ieee"` avoids TF32 input truncation but does not force the vendor reduction order. Naive tiled variants generally regress. Specialized row reductions sometimes improve warm-cache GEMV substantially; gains fall to roughly 1.1–1.3× with cache eviction. Their full-model experiment offers only about 1.7% combined latency improvement and changes waveform rounding despite exact tokens on 11 short inputs. These paths remain experimental, with numerical differences recorded rather than inferred to be perceptual quality loss.

NVIDIA's [floating-point emulation article](https://developer.nvidia.com/blog/unlocking-tensor-core-performance-with-floating-point-emulation-in-cublas/) describes BF16x9 FP32 emulation using multiple components/cross-products. The [cuBLAS documentation](https://docs.nvidia.com/cuda/cublas/) support table inspected on 2026-09-20 restricts this floating-point FP32 route to compute capabilities 10.0/10.3 with CUDA 12.9 or later. This RTX 5070 Ti is SM12.0 and is not listed. Fixed-point FP64 emulation support on 12.x is a different feature. Do not assume upgrading CUDA provides BF16x9 here; no such path or reduced-precision weights have been enabled.

Matched batching demonstrates a distinct throughput/latency tradeoff: batch 128 reaches 353.5/364.1 audio seconds per second encode/decode while only improving 1.06×/1.08× over equal-batch upstream eager. Its profile is roughly 80% SIMT SGEMM and 10% efficient attention. Thus matrix arithmetic dominates at larger batches, while graph launch elimination explains much of the small-batch gain. Both measurements guide further work; neither supports a 100× matched-workload claim.


## Fused and shared attention masks

The pinned upstream attention builds per-layer boolean masks from 64-bit query/key positions. A Triton kernel now computes the same causal/context tests and can write the FP32 additive bias directly, with row strides aligned to eight elements. `attention_mask_backend="triton"` enables it; synchronized stage calls reuse the bias while retaining separate KV tensors. External upstream streaming uses per-layer masks. Query/key/value projection, rotary arithmetic, SDPA, and output projection remain unchanged.

The [PyTorch 2.8.0 attention implementation](https://github.com/pytorch/pytorch/blob/v2.8.0/aten/src/ATen/native/transformers/attention.cpp) confirms that its ordinary boolean-mask conversion uses zero and negative infinity, followed by eight-element alignment for memory-efficient attention. Directly constructing these values avoids conversion and padding on every layer. This applies to the tested CUDA FP32 route; cuDNN's separate boolean conversion uses a finite sentinel, so do not generalize this implementation to reduced-precision/cuDNN paths. [SDPA documentation](https://docs.pytorch.org/docs/main/generated/torch.nn.functional.scaled_dot_product_attention.html) describes the boolean/additive semantics.

A shared-boolean intermediate reached 9.719/7.945 ms graph encode/decode; direct aligned additive construction reached 9.491/7.821 ms. The matched full upstream eager baseline for the final run was 48.369/38.571 ms, giving 5.10×/4.93×. Both residual backends retain exact outputs in the 12-case corpus, and corrected long streaming remains exact. Changes to attention reductions have not been introduced.

The new filled-ring profile (batch two, 80 ms chunks, full ten-second history) measures 11.665 ms encode and 10.208 ms decode per push. Dense GEMM kernel groups take roughly half the device time; memory-efficient attention takes 26.6% encode / 29.7% decode. Therefore streaming attention is now a substantial optimization target alongside weight-bandwidth-limited small-M matrices. Repeated cache offset operations remain candidates, but their individual kernels are below 1% each in this profile.


## FP32 split-cache attention research

Actual filled-ring activations confirm four attention geometries per direction at batch two / 80 ms chunks: (heads, queries, keys, width) = (20,1,125,64), (12,2,251,64), (12,4,503,64), (12,8,1007,64). The first geometry occurs in 32 layers; each other geometry occurs in 12. `benchmarks.attention_shapes` captures representative inputs after the ring fills, preserving their strides, and compares vendor SDPA, its math backend, an explicit FP32 Triton split-cache reduction, and optional compiled FlexAttention. Warm-cache and cache-evicted component times are separated from model measurements.

The [Flash-Decoding article](https://pytorch.org/blog/flash-decoding/) motivates splitting the key/value sequence to increase parallel work when query length is short. Its published lower-precision long-context speedups are not this codec's FP32 performance. Our prototype computes per-split maxima, denominators, and weighted-value sums, followed by a stable merge. Fully masked rows return zero. No TF32, FP16/BF16 operands, FP8/FP4, or weight conversion is used. Reduction order and exponential rounding differ from vendor SDPA, so this is an experimental numerical alternative, not an exact replacement.

`results/attention_shapes.json` records roughly 3–7× warm component improvements for the 64-key split, with smaller gains after cache eviction. Against FP64 diagnostics, error is often smaller than vendor FP32 but not uniformly so; closer-to-FP64 component results do not prove codec quality. The [FlexAttention inference article](https://pytorch.org/blog/flexattention-for-inference/) supplied a second comparison. Installed PyTorch 2.8 uses a quoted source literal for its precision option (`"'ieee'"`); the experiment explicitly requests it and disables TF32. FlexAttention is faster than SDPA here but slower than the custom split prototype, and is also nonbitwise (`results/attention_flex.json`).

Full streaming measurements use music, speech, and environmental audio at 12.8 seconds per lane; recordings shorter than that are explicitly repeated, with repetition counts in the report. Across two lanes and all 32 quantizers, all 30,720 tokens match the existing optimized stream. With fixed reference codes, maximum waveform differences are 1.69e-6 music, 2.10e-5 speech, and 8.51e-5 environmental audio, with respective signal-to-error ratios of 126.4, 118.2, and 102.0 dB. This is numerical evidence, not a listening study or universal no-quality-loss result. The prototype stays outside the supported runtime.

The prototype improves encoder latency from about 11.6–11.8 to 9.35–9.37 ms and decoder from about 10.13 to 7.84–7.85 ms per filled-ring push (1.24–1.26× / about 1.29× against the already optimized graph). These are approximately 20–21% / 22–23% latency reductions, not another 5× whole-model result. Further work should tune query reuse, examine near-tie quantizer decisions on more diverse recordings, and investigate attention reduction order if bitwise replacement is required.

A targeted test exposed stride-dependent Triton reduction trees when graph cloning densifies gapped Q/K/V tensors. The experimental wrapper now canonicalizes Q/K/V layout before launch and prevents specialization on bias row strides, which also affected the 256-key variant. Captured model buffers are already contiguous and require no copies; gapped caller inputs pay explicitly for normalization. Eager/graph equality is verified separately from tolerance-based comparison with vendor SDPA.


## Independent final lengths and fused lane reset

`StreamingSession.push` now accepts host `valid_lengths` and `final_lanes` sequences. A Triton preparation kernel masks invalid source positions before loading them, writes zero padding, computes effective lengths, and combines requested activity with persistent completion state. This avoids device-to-host reads for scheduling and safely ignores NaN audio or invalid code IDs in padding. A final partial encoder frame is retained; callers still track original sample counts for waveform trimming. Continuing lanes advance full chunks; partial positive tails must finish their lane. Empty completion skips model execution. Completed lanes remain inactive until reset, and the captured graph is reused.

Reset previously traversed every state and launched many small zero/where/copy operations. The new reset plan validates known state types, contiguous per-lane int64 offsets, and shared execution masks, then stores their addresses in a GPU table. One masked Triton kernel clears selected offsets and reopens selected lanes; unselected state remains unchanged. CPU offset bookkeeping retains upstream semantics. Unknown layouts/states fall back to original reset methods, and `fast_reset=False` is available for diagnostics. The plan releases state references on exit. [Triton cast documentation](https://triton-lang.org/main/python-api/generated/triton.language.cast.html) and [masked store semantics](https://triton-lang.org/main/python-api/generated/triton.language.store.html) are the relevant primitive references.

The full checkpoint's selected-lane reset falls from approximately 6.38 ms to 0.063 ms, about 101–102× for this control operation. This does not establish a 100× model speedup. The three-lane 71-step fidelity schedule retains 8,736 exact tokens and 522,240 exact audio samples against independent eager timelines using original resets, including 13 seconds of uninterrupted history before mixed tails/reuse. Same-shaped all-active timing isolates per-lane control overhead: about 0.05 ms encode and 0.10 ms decode in the final run, below 1% of per-push latency. Results include source hashes and explicitly repeated recordings/tokens.


## Exact cuBLASLt FP32 matrix layout research

Dense matrix multiplication remains the largest cost after the supported graph/fusion changes. The [cuBLAS 12.8 API documentation](https://docs.nvidia.com/cuda/archive/12.8.0/cublas/index.html) provides a useful route: cuBLASLt heuristic selection with `CUBLAS_COMPUTE_32F_PEDANTIC`, FP32 operands, and explicit row/column layouts. Legacy `CUBLAS_GEMM_ALGO0`–`23` selections have no effect on Ampere and newer hardware, so those IDs are not an effective tuning route on SM120. Pedantic FP32 does not itself guarantee the same reduction order as PyTorch; every proposed replacement is checked separately.

The research binding in `benchmarks/cublaslt.py` uses its own handle and the current CUDA stream, leaving PyTorch's handle/math mode untouched. It compares the original layout, an equivalent row layout, and a transposed contiguous FP32 weight copy. Tuning uses actual checkpoint weights/activations, separate warm and cache-evicted timings, FP64 error diagnostics, and eager/graph equality. A plan's buffers must outlive its captured graphs. Serial plans share a 32 MiB workspace, and operand alignment is validated.

One initial streaming attempt failed because its fresh heuristic shortlist omitted a previously measured descriptor. The binding now restores the measured opaque descriptor, requires the same cuBLASLt version, and calls `cublasLtMatmulAlgoCheck` for the operation/workspace. NVIDIA documents same-version descriptor serialization in the [algorithm type reference](https://docs.nvidia.com/cuda/archive/12.8.0/cublas/index.html#cublasltmatmulalgo-t). The experiment also rejects tuning from a different GPU name or PyTorch version. It does not substitute a different algorithm when the measured choice is absent from a new shortlist.

The two final sweeps record 1,118 component comparisons (with overlapping shapes). Several larger matrices retain bitwise equality while their selected transposed-layout algorithms improve warm/cold timings by roughly 1.3–1.8×. Smaller-row aggressive choices often change rounding; those are excluded. The selection rule requires exact captured output and graph replay, over 5% warm improvement, and over 10% cache-evicted improvement. Twenty-seven shape choices pass. Actual-weight stress checks add twelve activation variants per choice: recorded, negated, rescaled, zero, subnormal, tiny, large, sparse, and four random inputs. All 324 comparisons and graph replays are exact in `results/cublaslt_fidelity.json`.

Full-codec and long-stream gates are recorded in `results/full_cublaslt_experiment.json` and `results/full_cublaslt_streaming.json`. These preserve the original FP32 checkpoint and all quantizers. The offline corpus varies batch/chunk geometry while keeping 24 aggregate codec frames, and tests original-versus-packed eager and graph execution. The stream has eight lanes, 240 ms chunks, over ten seconds of uninterrupted history, independent pauses, tails, empty completion, and lane reuse. Benchmarks compare against the already optimized exact runtime, not the original eager baseline. Packed weights consume additional memory, and the implementation remains a research option under `benchmarks/`; the supported runtime and its approximately 5× batch-one table are unchanged.


## Single-copy resident FP32 weights

The initial packed-matrix experiment retained both original and transposed GPU weights. `benchmarks.packed_weights.PackedWeights` now shares a single packed tensor per Parameter across row-count plans. Its optional resident mode replaces the parameter's backing storage with a transposed view of that packed tensor. Parameter identity, logical dimensions, FP32 values, and arithmetic stay unchanged. On exit it reconstructs the original contiguous layout one parameter at a time after releasing the plans. There is no host offload or reduced-precision representation.

This uses the storage-sharing behavior of [PyTorch transpose](https://docs.pytorch.org/docs/main/generated/torch.transpose.html); a view changes dimensions/strides without another data allocation. A contiguous transpose makes the actual packed copy. Keeping a view back to the original dimensions allows the model to retain its logical weight values while cuBLASLt consumes the packed storage. Storage pointers and strides change during this research context, so old graphs and external aliases must not cross the transition. Frozen evaluation is required; overlapping matrix contexts and distinct Parameters sharing one storage are rejected. Unsupported matrix shapes reconstruct a temporary contiguous weight before ordinary linear execution. This preserves its original layout-dependent rounding, but can add copy overhead on those fallback calls. Autocast also follows that fallback path.

With the previous selected algorithms, the 14-case full-codec gate remains exact, including output checks after restoring the original layout. Peak allocated GPU memory falls from 13.25 to 7.45 GB while combined batch-eight latency stays approximately 26 ms. The long-stream gate remains exact with peak allocated memory falling from 11.64 to 8.74 GB. These are separate runs with identical workload geometry; they measure PyTorch allocated memory, not a claim about every allocator reservation or process-memory metric. The supported runtime defaults still do not enable experimental matrix replacement.

The broader batch sweep exposed a dispatch-specific fidelity issue that the flattened matrix stress gate could not detect: `encoder.7.output_proj` at batch 128 / one frame uses input shape `(128,1,1280)` and strides `(1280,1,1)`. It reports contiguous, but the leading strides do not satisfy PyTorch 2.8's `should_fold()` condition. The [pinned matmul source](https://github.com/pytorch/pytorch/blob/v2.8.0/aten/src/ATen/native/LinearAlgebra.cpp#L1783) therefore selects batched GEMM, whose rounding differs from flattening to 2-D GEMM. Tokens and audio were unchanged, but hidden states differed by up to 5.72e-6, so the initial batch gate was rejected (`results/full_cublaslt_batching_initial.json`).

A same-input layer audit returned reference outputs at each layer to prevent propagated errors and isolated that one projection across all three sources. The experimental wrapper now checks the pinned leading-stride folding rule in addition to contiguity, and preserves the native batched operation where folding would change dispatch. This applies to all matching layouts, not a layer-name exception. Tests exercise the fallback both before packing and after a different call has already packed the same weight. Matrix reports explicitly identify their flattened 2-D reference; future captures also retain native shape/stride metadata. The corrected layer audit and whole-codec rerun are retained alongside the rejected first attempt.


## Capability-based cuBLASLt search and matched confirmation

The next matrix experiment goes beyond the default heuristic shortlist using algorithm IDs, tile/stage capabilities, custom options, CTA swizzling, and split-K/reduction settings from the [cuBLAS API](https://docs.nvidia.com/cuda/archive/12.8.0/cublas/index.html). It initializes every candidate with pedantic FP32 compute and requires the capability flags for FP32 inputs, FP32 accumulators, and ordinary FMA. It retains all heuristic seeds and their split factors, including values outside the manually requested factors. Each operation descriptor passes `cublasLtMatmulAlgoCheck` before execution. This is a bounded search: one advertised custom range spans 262,144 values, so large ranges sample a prefix, individual bits, low-bit masks, and their maximum instead of claiming exhaustive enumeration.

The final search evaluates 12,422 valid configuration/layout/shape combinations on eight dominant actual-weight matrices at one, three, 24, and 384 rows. Only 350 are bitwise equal on the tuning activation. Finalists receive graph equality and separate warm/cache-evicted timing checks. Fifty-eight shape choices across this and prior reports pass the existing component selection rules, and all 696 actual-weight stress comparisons remain exact. Full-codec validation also remains exact on the 18-case real-audio batch sweep, including hidden states and restoration checks.

The whole-model outcome is a useful negative result. Alternating six rounds of previous/new resident configurations gives only **1.0072×** at batch one / one frame, **1.0004×** at batch eight / three frames, and **1.0026×** at batch 128 / three frames (`results/full_cublaslt_config_ablation.json`). These changes are below 1%, with overlapping timing variation in the first two cases. They do not justify replacing the existing default tuning or claiming another substantial model speedup.

A separate bracketing check (`cublaslt_confirm.py`) remeasures the baseline before and after each finalist. It exposes an unrepresentative initial baseline in the long search: the first row-one expansion matrix measured 65.18 microseconds initially versus roughly 34.12 microseconds during fresh confirmation. Thus its apparent roughly 6× warm ratio is not reliable; the repeated matched component result is roughly **3.1× warm**, and the selected custom option reaches only about **1.1×** after the eviction protocol. The actual model comparison remains decisive. Other warm winners can regress after eviction, and the three-row FFN shapes produce no useful exact improvement. Raw screening, confirmation, and full-model ablation reports are kept separately to avoid conflating them.

An algorithm reporting zero numerical capability flags was excluded from execution; a separate default-configuration support probe for ID 76 returned `CUBLAS_STATUS_NOT_SUPPORTED` in six tested shape/layout combinations (`results/cublaslt_unknown_capability.json`). This does not claim that every possible configuration of that ID is unavailable. Further work should change the optimization approach for the dominant matrix cost, rather than repeatedly searching the same vendor configuration space or treating warm-cache ratios as codec gains.


## Component-product tensor cores and a discrete fidelity failure

After the vendor search showed little remaining benefit, two Triton tensor-core prototypes were implemented with FP32 checkpoint storage and FP32 output. `tf32x3` uses Triton's three-product correction path. A separate manually implemented `bf16x6` path decomposes each operand into three BF16 components, evaluates six selected component products, keeps a separate correction accumulator, and adds the high-product block sums with explicit CUDA `add.rn.f32`. It is not the cuBLAS BF16x9 emulation feature, and does not require that feature's hardware support. Neither prototype changes the learned checkpoint, distills the model, or uses FP8/FP4.

Research motivation comes from [Ootomo and Yokota's single-precision tensor-core accuracy work](https://arxiv.org/abs/2203.03341) and its [quantum-circuit application](https://arxiv.org/abs/2303.08989), which discuss component corrections, accumulator rounding, and exponent range. Our kernels are experiments, not a port of their implementation or a reproduction of their A100 performance claims. [Triton's dot documentation](https://triton-lang.org/main/python-api/generated/triton.language.dot.html) describes the multi-pass precision options and the rounding caveat for ordinary TF32.

`tensorcore_shapes.py` measures original-weight matrices against FP64 diagnostics and exact PyTorch results, while separating warm/cache-evicted timing and eager/graph equality. Initial tiles have high register use; reducing tile sizes yields spill-free variants with 71 registers in a representative compact configuration. Larger dense matrices remain slower than vendor FP32 in these implementations. BF16x6 is closer to FP64 in some cases and farther away in others. None of the changed matrix paths is bitwise equivalent to the reference. This is evidence about the implemented kernels on SM120, not a claim that every possible tensor-core implementation must lose.

Direct paired comparison with the already tuned exact matrices (`tensorcore_select.py`) narrows the plausible case to a short QKV projection: `(M,N,K)=(24,3840,1280)`. TF32x3 is about 1.43× faster with warm weights, but only 0.87× as fast under the eviction protocol. A deliberately limited full-codec probe applies it to that QKV shape and leaves every other operation on the previous exact resident path. Combined batch-eight latency changes from approximately 26.015 to 25.392 ms, about 2.4%, but the candidate fails fidelity.

The 14-case probe changes **24 of 10,752 tokens** in one speech case. Maximum encoder hidden-state error there is only **8.58e-6**, yet maximum round-trip waveform error becomes **0.1522**, with RMSE **0.00646** and signal-to-error ratio **21.82 dB**. Holding original codes fixed reduces the decoder-only maximum difference to **1.23e-5**. Eager and graph outputs agree, so this is an arithmetic/quantization effect, not graph capture drift. `results/full_tensorcore_probe.json` records each changed quantizer/lane/frame coordinate and separates fixed-code decoding from the round trip.

`tensorcore_tie.py` traces the first changed decision using the full batch's original FP32 distance calculation. At zero-based quantizer 5, lane 6, frame 2, code IDs 198 and 1007 have reference squared distances **0.2859185934** and **0.2859187126**, a gap of **1.1920929e-7**. The small latent perturbation reverses their order. Further residual quantizers then produce additional changed tokens. These observations show why small matrix/latent RMSE and exact tokens on other clips do not establish quality preservation.

The candidate remains outside the runtime. Its failing eight-lane speech input is now part of `benchmarks.fidelity` as `speech_near_tie_b8_f3`, with source checksum and lane offsets recorded. Both supported residual backends pass the expanded 13-case corpus exactly. Future encoder arithmetic changes must face this regression alongside broader audio coverage; an approximate encoder would need a defensible strategy for discrete decisions, not just a small average-error claim.


## Stable-slot request scheduling and fused input gather

The existing masked streaming session could preserve independent lanes, but callers had to assign requests and refill slots themselves. NVIDIA's [sequence scheduling documentation](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/implicit_state_management.html#scheduling-strategies) explains why a stateful model with per-slot caches keeps each sequence in a dedicated slot and reassigns that slot after completion. `StreamingBatcher` implements this principle locally with FIFO admission, without adding an inference-server dependency. Active requests retain their slot, fixed batch shape, graph, and KV addresses. Finished or cancelled slots reset before reuse.

A Triton gather reads a small GPU table of source pointers, channel strides, offsets, and valid lengths. One launch copies the next input chunk from all assigned requests and zero-fills inactive lanes and tails; masked loads never dereference absent requests. The scheduler owns contiguous input copies on its construction stream, retaining them through the gather. It releases completed input storage and returns separately owned output chunks. Host metadata drives scheduling, so per-step output lengths do not require a device-to-host synchronization. Existing preparation kernels still handle effective encoder lengths and persistent completion state.

The isolated gather benchmark covers batch sizes 8/32/128 for audio and codes. All six cases are exact against zero-fill plus per-lane PyTorch copies. At batch eight, graph-amortized packing falls from **5.75 to 0.85 μs** for audio and **5.11 to 0.86 μs** for codes. At batch 128, ratios reach roughly 29×/25×. This component measurement has resident metadata and excludes its upload; it does not establish those gains for the model. The full-queue benchmark includes submission copies, metadata preparation, gather, resets, output ownership, and concatenation.

A heterogeneous queue of 16 requests uses frame counts `[129,3,6,9,12,15,18,21]` twice, with selected final audio tails shortened by 17 samples. Inputs cycle through the three hashed real-audio sources and are repeated explicitly where needed. The two longest requests each exceed ten seconds. Compared with admitting a new group of eight only after the previous group finishes, immediate refill reduces model steps from **86 to 44**, for the same **142 active chunk slots**. Useful slot occupancy rises from **20.64% to 40.34%**; the remaining tail inefficiency is visible rather than hidden by a peak-throughput claim.

Three alternating paired rounds on the full checkpoint yield median queue times **1837.35 → 941.75 ms encode** and **1669.98 → 857.26 ms decode**, about **1.951×/1.948×** over the same optimized runtime at the same batch size. All **13,632 code tokens** and **817,920 decoded samples** match original eager independent timelines at the same batch shape, with unchanged graph identity. A separate CuTe residual run is also exact and measures approximately 1.95× in both directions. There is no experimental tensor-core or matrix substitution in these runs. This is a scheduling improvement for the measured uneven queue, not an additional multiplier for the batch-one table. Equal-length queues can have no refill benefit.

The API accepts finite CUDA input tensors and permits new submissions between steps; it does not yet accept incremental input fragments or provide network serving. Queue capacity bounds request count, not bytes. Callers retain source audio lengths for final waveform trimming. Scheduling keeps a fixed batch size because changing it can change vendor arithmetic; the independent reference deliberately uses the same batch geometry. Wider input coverage, incremental request admission, cross-device execution, and reducing dense FP32 matrix cost remain necessary work toward the full objective.


## Exact LFQ selection, residual updates, and unused encoder outputs

The quantizer still launched many small operations after the earlier cache optimizations. `quantizer_backend="triton"` keeps the original normalization, FP32 vendor GEMM, codebooks, and all requested quantizers, while fusing the arithmetic around them. A row kernel computes `(row_norm - dots) + codebook_norm`, selects the index, gathers the original embedding, and optionally evaluates `latent + (embedding - latent)`. FP contraction is disabled. Both distance roundings and both straight-through roundings remain necessary: removing a common row norm can change a rounded tie, and simply returning the embedding can change cancellation results.

[Torch's maximum documentation](https://docs.pytorch.org/docs/main/generated/torch.max.html) specifies the first matching index for ties. Its [pinned reduction implementation](https://github.com/pytorch/pytorch/blob/v2.8.0/aten/src/ATen/native/SharedReduceOps.h) additionally prioritizes the first NaN. [Triton's argmin documentation](https://triton-lang.org/main/python-api/generated/triton.language.argmin.html) only promises its leftmost rule for non-NaN values, so the kernel explicitly reduces NaN indices separately. Tests include equal-distance codes, a rounding tie that would reverse if the row norm were dropped, infinities, and first-NaN selection.

The initial numerical kernel passed but a stride assertion failed for a gapped singleton-time input: the upstream addition produced `(8,1,8)` while the candidate allocated `(8,1,1)`. Although values were identical, layout-dependent downstream dispatch must not be assumed harmless. Noncanonical latent strides now use the original straight-through additions after fused selection; canonical convolution outputs retain the fused path. Raw embedding outputs preserve the original B,T,D allocation followed by transpose.

A second kernel combines the masked residual subtraction, next-step masking, and public quantized-vector accumulation. For the pinned encoder caller, the accumulated vectors are never returned or consumed: only code indices, lengths, and pre-quantizer hidden states are exposed. That path omits vector accumulation, its output projection, and the last quantizer's unused projected vector. It still computes the final code from the unchanged distance operation. Direct quantizer calls preserve all three original outputs. Local or global forward hooks disable the encoder-only omission so observers can still inspect those values. A temporary flag is restored even on exceptions; CUDA graphs capture the selected path normally.

The public quantizer still returns its vectors, so its timing is distinct from the encoder-only omission. All measured quantized vectors, indices, lengths, and encoder codes remain exact. The preliminary selector-only report is retained separately; its first 1×1 encoder baseline was much slower than later matched baselines, so that initial ratio is not a model performance claim. The final three-round ablation is authoritative.

Both Triton and CuTe residual configurations pass the 13-case full-model corpus with quantizer fusion, including the speech decision separated by only 1.19e-7. The 16-request long queue also remains exact against original eager timelines: 13,632 tokens and 817,920 decoded samples, with lane reuse and two requests beyond ten seconds. These are tested-input guarantees, not a universal proof for arbitrary data or changed libraries.

Paired full-model profiles show **2,054 → 1,727 encoder kernels per replay**, a reduction of 327, including 32 fused selectors and 31 residual-update kernels. Decoder execution stays at **1,182 kernels**. Dense FP32 SGEMM-named kernels remain **77.10%** of encoder and **80.04%** of decoder GPU kernel time in the new profile. This confirms the next priority: the dominant matrix cost remains, despite useful exact fusion gains. The supported fusion is opt-in and does not establish 100× acceleration.
