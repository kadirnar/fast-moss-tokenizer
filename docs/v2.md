# MOSS Audio Tokenizer v2

The active target is [OpenMOSS-Team/MOSS-Audio-Tokenizer-v2](https://huggingface.co/OpenMOSS-Team/MOSS-Audio-Tokenizer-v2), pinned to `f6e20e543b33d2c252a7ef71bdf8aa71e5ff9169`: 2,123,701,248 parameters, 48 kHz stereo and 32 quantizers. The older [v1 implementation](v1.md) targets a separate 24 kHz mono checkpoint. Its speedups and streaming scheduler do not apply to v2.

## Precision and optimizations

Both the baseline and optimized v2 model use the checkpoint's native policy: FP32 parameters, BF16 codec compute, FP32 normalization/scales and FP32 quantizer. SDPA is explicit in both paths; the optional FlashAttention package is absent in this environment. TF32 is disabled. No weights are trained, distilled or replaced, and no FP8/FP4 path is used.

`fast_moss.v2.optimized(model)` caches the exact BF16 casts of 760 linear layers and the FP32 normalized weights of 66 convolutions. It also caches normalized codebooks, uses the validated CUDA LFQ preparation kernel and a Triton distance/argmin/embedding kernel, and retains the vendor FP32 quantizer matrix multiplication and the original straight-through arithmetic. The casts reproduce operations that the original model already performs. The runtime adds approximately 4.25 GB of cached tensors to the 8.49 GB FP32 checkpoint.

The default pointwise path additionally fuses RoPE rotations and both scaled residual additions in all 184 transformer layers. RoPE reads BF16 Q/K, computes each multiplication/addition in FP32 and casts each final component back to BF16, matching the [pinned upstream implementation](https://huggingface.co/OpenMOSS-Team/MOSS-Audio-Tokenizer-v2/blob/f6e20e543b33d2c252a7ef71bdf8aa71e5ff9169/modeling_moss_audio_tokenizer.py). Frequencies are cached; phase, sine and cosine remain native PyTorch operations. Residual kernels promote BF16 updates before multiplying the FP32 scale and adding the residual. LayerNorm remains native, consistent with [PyTorch 2.8 autocast](https://github.com/pytorch/pytorch/blob/v2.8.0/aten/src/ATen/autocast_mode.cpp). Both kernels disable the multiply/add fusion exposed by the [Triton 3.4 compiler](https://github.com/triton-lang/triton/blob/v3.4.0/third_party/nvidia/backend/compiler.py), retaining the original separate roundings. `optimized(model, pointwise=False)` reproduces the preceding cached runtime for ablation.

Gradient requests, changed RoPE periods, unsupported layouts/dtypes and observed scale-module hooks use native fallbacks where applicable. Scale hooks retain their native calls. Managed context exit restores all patched forwards and releases frequency caches. Stress tests cover BF16/FP32 inputs, native QKV strides, changed graph inputs, different streaming offsets, subnormals, signed zeros, infinities and NaNs at the bit level.

The context is reversible and belongs to one host thread. Parameters must be frozen and on one CUDA device. Eager wrappers fall back to original methods if relevant weight identities/versions change or gradients are requested. Keep model parameters, methods, hooks and precision settings fixed for the lifetime of a captured graph: Python guards do not run during replay. Managed graphs expire when an optimization context starts or exits. Model parameters created as inference tensors without version counters are not supported; use the supplied loader.

## Fixed offline graphs

`codec(model, audio)` accepts contiguous or strided FP32 audio shaped `[batch, 2, samples]`, with all lanes the same length and `samples` a positive multiple of 3,840 (80 ms). It returns codes, encoder hidden states and reconstructed stereo audio. `GraphedCallable` returns owned copies of its outputs and accepts new inputs with the same shape, dtype and device on its construction CUDA stream. Keep it inside the optimization context.

Upstream `_encode_frame` reads a valid length with CUDA `.item()`, which prevents capture. `encode_fixed` reproduces its tensor operations for complete equal-length frames while omitting this redundant host synchronization and full-length slice. Both the original graph adapter and optimized graph use this same adapter. It is checked against original eager encoding. The table's original graph column is therefore explicitly an **adapter**, not an unmodified upstream CUDA graph.

For tails or different valid lengths, use the upstream `model.encode` / `model.batch_encode` APIs and their padding/length handling. Do not send partial frames to `encode_fixed`.

## Native streaming

V2's native streaming calls retain causal context across chunks:

```python
from fast_moss.v2 import load_model, optimized
import torch

model = load_model()
audio = torch.zeros(1, 2, 48_000, device="cuda")
with torch.inference_mode(), optimized(model):
    encoded = model.encode(audio, return_dict=True, chunk_duration=0.08)
    decoded = model.decode(encoded.audio_codes, return_dict=True, chunk_duration=0.08)
```

These APIs process the supplied waveform in successive chunks. The offline graph helper does not carry streaming state. V1's `StreamingSession` and `StreamingBatcher` are not v2 APIs. Streaming correctness is compared against original v2 streaming, separately from offline graph performance; no optimized streaming latency claim is made.

## Reproduce

Install the pinned environment from the root README, then run GPU jobs sequentially:

```bash
.venv/bin/python -m benchmarks.fetch_audio
.venv/bin/python -m benchmarks.v2_baseline
.venv/bin/python -m benchmarks.v2_compare --warmups 200 --output results/v2_pointwise_compare.json
.venv/bin/python -m benchmarks.v2_compare --cached-ablation --warmups 200 --output results/v2_pointwise_ablation.json
.venv/bin/python -m benchmarks.v2_fidelity --output results/v2_pointwise_fidelity.json
.venv/bin/python -m benchmarks.v2_fidelity --streaming --batch 1 --output results/v2_pointwise_streaming_b1.json
.venv/bin/python -m benchmarks.v2_fidelity --streaming --batch 2 --output results/v2_pointwise_streaming_b2.json
.venv/bin/python -m pytest -q
.venv/bin/python -m benchmarks.v2_profile --output results/v2_pointwise_profile.json
.venv/bin/python -m benchmarks.v2_pointwise_resources
```

The measured real recording is a stereo 44.1 kHz train whistle, resampled to 48 kHz with both original channels preserved. It is not duplicated mono. The fidelity corpus also includes independent 18/21 kHz tones created directly at 48 kHz, swapped/isolated channels, silence, separate channel impulses, tiny signals, batch sizes one/two and 80/240/960 ms lengths. Changed graph inputs are compared against references computed outside the optimization context.

Long streaming checks cyclically extend the 2.48-second recording to 12.96 seconds (162 chunks) with distinct lane offsets. This checks execution equivalence on a small regression corpus, not a comprehensive perceptual evaluation. Bit identity is relative to original v2 with the same precision policy, backend, hardware and pinned software.

The performance comparison rotates original eager, original graph adapter and optimized graph for three rounds. Each graph receives 200 extra warmup replays; each mode contributes ten timed calls per round. Times include input copies and owned output copies, with model and input resident on GPU. File I/O, resampling, model loading, cache construction and graph capture are excluded. Ratios are measured directly, not multiplied from component improvements.

## Remaining costs

The [initial cached-runtime profile](../results/v2_profile.json) recorded 14,402 original graph kernels versus 13,030 cached-runtime kernels. It identified FP32 pointwise arithmetic and BF16 GEMV as remaining targets, motivating the pointwise fusion above. The [updated profile](../results/v2_pointwise_profile.json) records the current kernel costs. Profiler durations are diagnostic and separate from the README's wall-clock latency.
